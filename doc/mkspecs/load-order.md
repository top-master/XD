# Feature load order

qmake wraps every project (`.pro`) it evaluates with feature (`.prf`) files:
some load before the project body (the "pre" hooks) and some after (the "post"
hooks). A config decision (anything that reads or edits `CONFIG` or `QT_CONFIG`)
only works if it runs after the values it tests are set, and before whatever
consumes them.

The trap: the platform scopes `win32`, `winrt`, `msvc` (and `MSC_VER`) are NOT
in `CONFIG` while the spec itself is loading. qmake adds them later. So a check
written in `mkspecs/qconfig.pri` (which loads via the spec) sees them empty and
misfires, most visibly on a cross build, where the platform comes from the
`-xspec`, not the `-spec` (see [host_build](./modes/host_build.md)).

## `QMAKE_PLATFORM` versus the `win32` / `winrt` / `msvc` scopes

These look interchangeable but are set at different times, which is the whole
reason the order matters:

- `QMAKE_PLATFORM` is a plain variable the spec assigns in its `qmake.conf`
  (for example `win32-g++/qmake.conf` sets `QMAKE_PLATFORM = win32 mingw` near
  the top, before its own `load(qt_config)`). So it is readable from the moment
  the spec starts loading, `qconfig.pri` included.
- `win32`, `winrt`, `msvc` (and `MSC_VER`) are `CONFIG` scopes that qmake
  derives and adds *later*, not during spec load. They are only reliably in
  `CONFIG` by the time `default_pre.prf` runs.

So the same test gives different answers depending on where it sits. A quick
probe makes it concrete: `$$find(CONFIG, ^win32$)` from `qconfig.pri` prints
nothing, while the same probe from `default_pre.prf` prints `win32`. On a cross
build the gap is wider still, because the platform arrives via the `-xspec` (the
target spec), which is resolved later.

Practical rule: for a platform test that must run at spec time, key off
`QMAKE_PLATFORM` (this is exactly what `spec_post.prf` does, e.g.
`contains(QMAKE_PLATFORM, win32)`); only rely on the `win32` / `winrt` / `msvc`
scopes from `default_pre.prf` onward.

## Pre-project load order

For a win32 cross target (`-spec linux-g++ -xspec win32-g++`), the places loaded
before the project body, in order:

| # | place | `win32` in CONFIG? | scope and role |
|---|-------|--------------------|----------------|
| 1 | `features/spec_pre.prf` | no | earliest; seeds base `CONFIG` (`qt`, `isXD`) |
| 2 | `<spec>/qmake.conf` -> `features/device_config.prf` | no | per-device; empties `CROSS_COMPILE` for host builds |
| 3 | `features/qt_config.prf` (and `win32/qt_config.prf`) -> `mkspecs/qconfig.pri` | no | loads `QT_CONFIG` |
| 4 | `features/spec_post.prf` | only `QMAKE_PLATFORM` | re-loads `qt_config`; the platform scopes are still unreliable |
| 5 | `features/default_pre.prf` | yes | generic; every project |
| 6 | `features/win32/default_pre.prf` | yes | win32 only; every win32 project |
| 6b | `features/win32/windows.prf` | yes | pulled in via `CONFIG += windows` during feature resolution, after the SUBDIRS gate |
| 7 | `exclusive_builds`, `qt_functions`, `xd_functions` | yes | loaded inside #5; function libraries |

The project body runs after #7, then `default_pre`'s counterparts
`default_post.prf` (and `win32/default_post.prf`) run as the "post" hooks.

## Where a config decision belongs

The first places with the full `CONFIG` settled are #5 and #6. So a check that
reads `win32` / `winrt` / `msvc` and edits `QT_CONFIG` for the whole build
belongs there (or in an XD-owned file loaded from there, such as
`xd_functions.prf`, #7), NOT in the spec-time files #1 to #4.

`win32/default_pre.prf` (#6) is already win32-scoped, so a `win32:` guard inside
it is redundant. This is exactly why the Windows OpenGL/ANGLE auto-skip cannot
live in `qconfig.pri` (#3): there, `win32` is not set yet.

## Can the scopes be set earlier instead?

Tempting (it would avoid relocating anything), but only partly possible, and not
for the ANGLE case. `win32` enters `CONFIG` at exactly one line,
`spec_post.prf`'s `CONFIG += $$QMAKE_PLATFORM` (#4), and `QMAKE_PLATFORM` is
already set by the spec's `qmake.conf` before it loads `qconfig.pri`. So `win32`
on its own could be forced early with the same `CONFIG += $$QMAKE_PLATFORM` at
the top of `qconfig.pri`.

But a check like the OpenGL/ANGLE skip also reads `winrt`, `msvc`, and
`MSC_VER`, and those are not all knowable that early:

- `winrt` and `msvc` are not in `QMAKE_PLATFORM` for `win32-g++` (it is just
  `win32 mingw`); the MSVC distinction arrives through a different spec.
- `MSC_VER` is set in each MSVC spec's `qmake.conf` but `msvc-desktop.conf` then
  does `unset(MSC_VER)` (moving it to `QMAKE_MSC_VER`), so its lifetime is spec
  load only, and it is spec-conditional.

On top of that, `qconfig.pri` is generated by `configure` (it writes
`QT_LICHECK`, the zlib lines, and so on), so platform logic added there is
fragile: a reconfigure rewrites the file. Forcing the platform in early also
fights qmake's single designed injection point, `spec_post.prf`.

So the rule splits by what the check needs. A check that needs only `win32` can
set it early; a check that needs the full `win32` / `winrt` / `msvc` / `MSC_VER`
picture (the ANGLE skip) belongs at #6, where they are all settled. Relocating
wins there because the values genuinely do not exist yet at #3, not merely
because it is tidier.

`QT_LICHECK` (`win32: QT_LICHECK = licheck.exe` in `qconfig.pri`) is the milder
variant: its only reader is `default_pre.prf` (#5), so the writer does precede
the reader, but the `win32:` at #3 still misfires on a cross build and takes the
empty `else` branch. In practice it is benign here: for the OpenSource edition
licheck is not enforced, and licheck runs on the host, so an `.exe` suffix chosen
from the *target* would be wrong on a Linux-host cross build regardless. If it
ever needs to be correct, the fix is to key the suffix off the host, or set it in
`default_pre.prf` ahead of line 27, not to trust `win32:` in `qconfig.pri`.
